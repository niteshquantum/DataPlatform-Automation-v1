1. EXECUTIVE SUMMARY
================================================================================

The Jenkins dataset pipeline supports two source types: Google Drive and local.
The current implementation downloads/acquires a dataset, extracts it if it is a
ZIP archive, and verifies the result. A separate Jenkins stage performs download
verification.

Key finding: The Verify Download stage fails on Windows Jenkins agents because
the Jenkinsfile invokes `python3` instead of `python`. This is a blocking bug
that makes the second stage always fail, even when the download stage succeeds.

Additional design gap: When FORCE_DOWNLOAD=false and an existing archive is
valid, the system reuses it without checking whether it matches the current
source URL. This means a different Google Drive URL with the same configured
filename would reuse the old archive.

8. GOOGLE DRIVE BEHAVIOR
================================================================================

Current behavior:
  - Uses gdown library for download
  - gdown converts Drive view URL to direct download URL (uc?id=...)
  - Downloads to temp file in destination directory
  - Validates archive after download
  - Renames temp to final filename
  - Records state with sha256, source_url, timestamp

SOURCE_PATH override:
  - If Jenkins SOURCE_PATH is provided, it overrides config DATASET_URL
  - If Jenkins SOURCE_PATH is empty, falls back to config DATASET_URL
  - The output filename ALWAYS comes from config DATASET_NAME
  - The Drive file ID is NOT explicitly tracked (only the full URL in state)

Repeated same source:
  - If FORCE_DOWNLOAD=false and archive exists and validates:
    Download is skipped. State is NOT updated.
  - Extraction skip logic checks:
    * archive path matches state
    * archive sha256 matches state
    * all expected folders exist in incoming/
  - If all match, extraction is skipped

Different source, same filename:
  - Output filename is always TestingDataset.zip (from config)
  - If FORCE_DOWNLOAD=false:
    * Existing TestingDataset.zip is validated as ZIP
    * If valid, download is SKIPPED
    * Old archive is reused regardless of source URL
    * State still has old source_url
  - If FORCE_DOWNLOAD=true:
    * New download overwrites old archive
    * State is updated with new source_url and sha256
    * Extraction runs because download_timestamp > extraction_timestamp

Risk: FORCE_DOWNLOAD=false does NOT verify source identity. A different Drive
URL producing a valid ZIP with the same filename would be silently reused.

10. ARCHIVE BEHAVIOR
================================================================================

Archive naming:
  - Fixed by source_utils.get_output_filename()
  - Google Drive: always config["DATASET_NAME"]
  - Local file: source path basename
  - No dynamic/duplicate naming (no "TestingDataset (1).zip")

Archive preservation:
  - Archive is kept in incoming/archive/ by default
  - DELETE_ARCHIVE=false in current config
  - If DELETE_ARCHIVE=true, archive is deleted after successful extraction

Archive reuse:
  - If FORCE_DOWNLOAD=false and archive exists and validates as ZIP:
    Download is skipped entirely
  - No source URL comparison on existing archive
  - No timestamp comparison on existing archive
  - Only ZIP structural validation is performed

Archive overwrite:
  - New download uses temp file, then atomic rename
  - Old archive is replaced, not merged
  - No duplicate filename creation

11. EXTRACTION BEHAVIOR
================================================================================

Tool:
  - Primary: Python zipfile module
  - Fallback: 7-Zip (for unsupported compression like Deflate64)

Destination:
  - incoming/ (project root)
  - Top-level folders from archive are extracted directly under incoming/

Overwrite behavior:
  - extract_and_merge_zip() explicitly unlinks existing files before writing
  - PermissionError during unlink triggers warning, then attempts overwrite
  - zipfile.extractall() with 7-Zip fallback also overwrites

Stale files:
  - Extraction is merge-based, not clean-based
  - If new archive has fewer files than old extraction, old files remain
  - Example: old archive had mongodb/, mssql/, mysql/, postgresql/
            new archive has only mssql/, mysql/
            mongodb/ and postgresql/ folders remain in incoming/

Fresh download detection:
  - Compares download_timestamp vs extraction_timestamp in state
  - fresh_download = True if download_ts exists and (no extraction_ts or download_ts > extraction_ts)

Extraction skip:
  - can_skip = not FORCE_EXTRACT and not fresh_download and extraction_status == "EXTRACTED_COMPLETE"
  - If can_skip, additionally checks:
    * archive path matches state archive_path
    * archive sha256 matches state dataset_identity
    * all expected folders exist in incoming/
  - If any check fails, re-extraction occurs

Partial extraction:
  - If extraction fails halfway, partial files/folders remain
  - No cleanup of partial extraction
  - State is marked EXTRACTED_INVALID only if post-extraction folder check fails
  - During extract_and_merge_zip, exceptions propagate and partial files remain

12. VERIFICATION BEHAVIOR
================================================================================

Two verification mechanisms exist:

A. extract_dataset.py -> verify_dataset()
   - Built into the download stage
   - For archives:
     * Checks archive exists OR incoming has data
     * Lists top-level folders from archive
     * Verifies each folder exists in incoming/
     * Prints "[OK] Verified folder: <name>"
   - For non-archives:
     * Prints generic success message

B. verify_download.py (separate Jenkins stage)
   - For archives:
     * Checks incoming/archive/<filename> exists
     * Prints file size
   - For non-archives:
     * Checks incoming/<database>/ exists and has files
     * Lists files

Relationship:
  - These are overlapping/duplicate, not complementary
  - verify_dataset() checks folder structure after extraction
  - verify_download.py checks archive presence (or incoming files for non-archive)
  - For archives, verify_download.py does NOT check folder structure
  - For non-archives, verify_dataset() is minimal while verify_download.py is more thorough

Current issue:
  - Verify Download stage fails due to python3/python issue
  - So this verification is currently non-functional in Jenkins

  Needed: Parameterize DATABASE to support other database types
  Impact: Cannot run pipeline for MySQL/PostgreSQL datasets without code change

  Impact: Large datasets take longer than necessary

GAP-7: State file is single-dataset
  metadata/common/dataset_state.json tracks only one dataset
  Impact: Cannot track multiple datasets or pipeline runs independently

GAP-8: No retry logic for transient failures

18. RISKS
================================================================================

RISK-1: Wrong dataset reused silently
  When FORCE_DOWNLOAD=false and a valid archive exists, the system does not
  verify that the archive matches the current source. A different Drive URL
  producing a same-named ZIP would be silently reused.

RISK-2: Stale extracted data
  Merge-based extraction does not clean old files. A new dataset with fewer
  tables leaves old extracted files in incoming/.

RISK-3: Partial extraction without cleanup
  If extraction fails, partial data remains. Next run may skip extraction
  (if state says complete) or re-extract on top of partial data.

RISK-4: Verification stage always fails on Windows
  The python3/python mismatch means the Verify Download stage never passes
  on Windows Jenkins. This masks real verification issues.

RISK-5: State file corruption
  dataset_state.json is a single flat file with no backup. Corruption or
  concurrent writes could lose state.

RISK-6: 7-Zip dependency not verified before use
  7-Zip is installed in the download stage but not re-verified before
  extraction. If 7-Zip installation silently fails, extraction would fail
  on archives requiring 7-Zip.
