1. EXECUTIVE SUMMARY
================================================================================

This proposal fixes the source-identity bug while preserving all currently
working behavior. The fix is a minimum-change extension of the existing
dataset state mechanism.

Two changes are required:
  1. Extend dataset_state.py to record the resolved source URL.
  2. Add a source-identity check in download_dataset.py before reusing an
     existing archive.

No new files. No new frameworks. No refactoring of verification logic.

================================================================================
2. CURRENT WORKING BEHAVIOR — MUST PRESERVE
================================================================================

Google Drive:
  - Jenkins SOURCE_PATH overrides config DATASET_URL
  - Archive downloads to incoming/archive/<DATASET_NAME>
  - ZIP extracts to incoming/
  - Same source reuse optimization (FORCE_DOWNLOAD=false) preserved

Local folder:
  - CSV/JSON files copy to incoming/<database>/
  - Existing files overwritten
  - Spaces in paths work

Local ZIP:
  - File copies to incoming/archive/
  - Extracts to incoming/

Same source reuse:
  - Valid existing archive → skip download
  - Valid existing extraction → skip extraction

4. SOURCE IDENTITY DESIGN
================================================================================

RECOMMENDED APPROACH: Option D — Compare source type + source URL + archive SHA256

Rationale:
  - Source type prevents cross-source-type confusion (google_drive vs local)
  - Source URL is already partially tracked (state.source_url exists but is
    populated from config, not from the resolved runtime value)
  - Archive SHA256 is already computed and stored as dataset_identity /
    archive_sha256
  - No new state fields are required
  - No new dependencies are required
  - Works for all three source types (google_drive, local file, local folder)

What changes:
  - dataset_state.py: build_download_state() accepts the resolved source_url
    and source_type as parameters instead of reading them from config.
  - download_dataset.py: passes resolved source_type and source_url to
    build_download_state(), and uses them in the skip logic.

Source URL resolution (already exists in download_dataset.py):
  - google_drive: os.getenv("SOURCE_PATH") or config.get("SOURCE_PATH") or config.get("DATASET_URL")
  - local: os.getenv("SOURCE_PATH") or config.get("SOURCE_PATH")
  - The resolved value is what the downloader actually uses.

================================================================================
5. SAME SOURCE DECISION FLOW
================================================================================

SOURCE A + existing archive + FORCE_DOWNLOAD=false

Step 1: output_file exists?
  NO  → Download fresh
  YES → Continue

Step 2: Archive validates as ZIP?
  NO  → Re-download (existing file is corrupt)
  YES → Continue

Step 3: Load state
  No state file → Continue to download

Step 4: source_type matches state?
  NO  → Download fresh
  YES → Continue

Step 5: source_url matches state?
  NO  → Download fresh
  YES → Continue

Step 6: archive SHA256 matches state dataset_identity?
  NO  → Download fresh (archive was modified)
  YES → Continue

Step 7: Skip download. Reuse existing archive.

Step 8: Extraction skip (existing logic):
  - extraction_status == "EXTRACTED_COMPLETE"
  - not FORCE_EXTRACT
  - not fresh_download
  - archive path matches state
  - archive SHA256 matches state
  - all expected folders exist in incoming/
  → Skip extraction

================================================================================
6. DIFFERENT SOURCE DECISION FLOW
================================================================================

SOURCE B + existing archive from SOURCE A + FORCE_DOWNLOAD=false

Step 1-3: Same as same-source flow

Step 4: source_type matches state?
  NO  → Download fresh (with warning log)
  YES → Continue

Step 5: source_url matches state?
  NO  → Download fresh (with warning log)
  YES → Continue (this means same source)

Expected behavior when source differs:
  - Log: [WARNING] Source identity mismatch.
  - Log: [WARNING] Current source: <current_source_url>
  - Log: [WARNING] State source:   <state_source_url>
  - Log: [INFO] Downloading current source...
  - Proceed with download
  - Replace archive atomically (temp + rename)
  - Update state with new source_url and SHA256
  - Extraction runs because download_timestamp > extraction_timestamp

RECOMMENDATION: Auto-download with clear warning.
  Reason: Jenkins pipelines must be automated. Failing and requiring manual
          intervention breaks the pipeline. A warning provides visibility.

================================================================================
7. FORCE_DOWNLOAD DECISION FLOW
================================================================================

SOURCE B + FORCE_DOWNLOAD=true

Step 1: output_file exists?
  YES → Continue (will overwrite)
  NO  → Continue (will create)

Step 2: Skip ALL identity checks (force flag takes precedence)

Step 3: Download to temp file

Step 4: Validate archive

Step 5: Atomic rename (replaces existing archive)

Step 6: Update state with new source_url, SHA256, timestamp

Step 7: Extraction runs (fresh_download = True because download_ts > extraction_ts)

Current implementation already does this correctly. No changes needed.

9. EXTRACTION CLEANUP DESIGN
================================================================================

RECOMMENDATION: Option B — Clean only folders present in previous dataset state.

Rationale:
  - Option A (clean all incoming/) is too aggressive — may remove unrelated data
  - Option C (temp extraction + atomic replace) is a larger architectural change
  - Option B uses existing state field `validated_extracted_structure`

Implementation:
  - Before extract_and_merge_zip(), load state
  - Get previous folders from state.get("validated_extracted_structure", [])
  - Remove those folders from incoming_path if they exist
  - Then extract fresh

Scope:
  - Only applies to archive extraction (not local folder copy)
  - Controlled by existing config or implicit (always clean previous structure)

Minimum change location:
  - extract_dataset.py, function extract_dataset(), before calling extract_and_merge_zip()

================================================================================
10. PARTIAL EXTRACTION RECOVERY DESIGN
================================================================================

RECOMMENDATION: Wrap extract_and_merge_zip() in try/except and mark state
invalid on any failure.

Current behavior:
  - If extraction fails, partial files remain in incoming/
  - State is NOT updated (still says EXTRACTED_COMPLETE from previous run
    or never set for first run)
  - Next run may skip extraction incorrectly if state is stale

Minimum change:
  - In extract_dataset.py, wrap the extract_and_merge_zip() call:
    ```python
    try:
        extract_and_merge_zip(archive_file, incoming_path)
    except Exception as exc:
        mark_extraction_invalid(str(exc))
        raise
    ```
  - This ensures state reflects failure
  - Next run will re-extract because extraction_status != "EXTRACTED_COMPLETE"

Note: This does NOT clean partial files. That would require the Option B
cleanup from section 9. The state fix alone prevents incorrect skip behavior.

They are overlapping but not identical. Merging them would be a refactor,
not a minimum change. Leave them as-is.

17. BACKWARD COMPATIBILITY ANALYSIS
================================================================================

State file format:
  - Current: flat JSON with fields like source_url, dataset_identity, etc.
  - After change: same flat JSON, plus source_type field
  - Old state files without source_type: treated as mismatch → re-download
  - This is safe: a missing field triggers fresh download, not silent reuse

Archive naming:
  - Unchanged. Google Drive uses DATASET_NAME, local uses source filename.

Skip behavior:
  - Same source: identical behavior (skip download, skip extraction)
  - Different source: NEW behavior (re-download instead of silent reuse)
  - FORCE_DOWNLOAD=true: identical behavior

Local folder:
  - Unchanged. No archive, no state check, direct copy.

Extraction:
  - Pre-cleanup removes only folders from previous state
  - If no previous state, no cleanup
  - If state is corrupted/missing, no cleanup (safe default)

20. RISKS / TRADEOFFS
================================================================================

RISK-1: Source URL normalization
  Different representations of the same URL (trailing slash, http vs https,
  query parameter order) would be treated as different sources.
  MITIGATION: Acceptable for current use case. Drive URLs from gdown are
  normalized. Local paths use Path.resolve() for comparison in state.

RISK-2: State file corruption
  If dataset_state.json is corrupted, load_state() returns {} and the system
  re-downloads. This is safe (fail-open for download).
  MITIGATION: Existing try/except in load_state() handles this.

RISK-3: Concurrent pipeline runs
  Two simultaneous runs could race on state file writes.
  MITIGATION: Not in scope. Current architecture does not support concurrent
  runs. Jenkins disableConcurrentBuilds() in migration pipeline suggests
  this is a known constraint.

RISK-4: Pre-extraction cleanup removes user data
  If someone manually added files to incoming/<folder>/, they would be
  removed before extraction.
  MITIGATION: Cleanup only targets folders recorded in previous state, which
  were created by the pipeline. This limits blast radius.

TRADEOFF: We chose source URL comparison over Drive file ID because:
  - File ID requires parsing the Drive URL (adds complexity)
  - Source URL is already available and human-readable
  - For local sources, path serves the same identity purpose
  - If Drive file ID becomes critical later, it can be added to state
    without breaking the current design.
